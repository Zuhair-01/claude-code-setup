# Alwazour Product Visualization Engine

**Purpose:** Transform every Alwazour product into an accurate, technically meaningful visual experience that explains what the product is, how it's constructed, why its specifications matter, and where it's used.

**Governing principle:**
> **Do not decorate the product. Explain the product visually.**

All visualizations trace back to real data in `data/real/products.csv` (and the schema it imports into, `src/schema/product.ts`). Never invent specifications, materials, dimensions, connector shapes, or internal structures not supported by that data — see §5.

---

## 0. THE REAL STACK — read this before touching anything

The alwazour site is **zero-dependency Node + TypeScript, hand-rolled SVG/CSS/vanilla JS**.
No React, no Vite, no Three.js, no GSAP, no WebGL, no build step beyond
`node --experimental-strip-types`. This is a deliberate, documented decision
(`docs/REVAMP_PLAN.md`), driven by the actual target: throttled-3G Syrian
mobile connections, where a WebGL/GLTF pipeline is dead weight, not a feature.

An earlier version of this skill described a React Three Fiber / GSAP /
Zustand pipeline with `.tsx` components and a `getProduct()` data loader.
**None of that exists in this repo** — it described a stack this project
explicitly rejected, using file paths and example SKUs that were never real.
If you're tempted to reach for a 3D/animation library, that's the signal
you've drifted from what this project actually is. Every visualization here
is inline SVG generated by a plain TypeScript function, animated by one
shared scroll-progress CSS engine (§3).

### Real file map

| File | What it generates |
|---|---|
| `src/site/connectors.ts` | `connectorMacro(kind, lang)` — one SVG anatomy drawing per real connector family (RJ45, HDMI, USB-C, XLR, DB9, phone jack mono/stereo, DC barrel, fibre, …). Dispatches purely off the connector token string; order matters (specific before general). `CONNECTOR_IDS` lists every family it can draw. |
| `src/site/diagrams.ts` | Shared diagram primitives: `cableCrossSection`, `devicePanel` (a real port bank, N sockets from real `PortSpec[]` data), `networkTopology` (tiered node graph, now with real icon glyphs — see §3), `rackElevation` (a real cabinet with a hinged door that opens on scroll — see §3), `cameraCoverage`. |
| `src/site/product-visuals.ts` | Routes each product to a story template by `resolveVisualType()` (`cable`/`connector` → `cableStory`, `extender`/`switch` → `deviceStory`, `camera` → `cameraStory`, `rack` → `rackStory`, `pbx` → `pbxStory`, everything else → `genericStory`). `genericStory` also renders real connector anatomy when the product has confirmed `connectors` data, not just a bare chassis. |
| `src/schema/product.ts` | The real data model. `resolveVisualType()`, `Presentation.visualType`, `technicalData.ports`, `technicalData.connectors`, `relationships.alternatives`. |
| `src/schema/solution.ts` | Solution pages (a real requirement chain resolved against live stock, never a hardcoded SKU list). `Solution.signalChain` is the honest way to add source/destination context nodes to a topology diagram without inventing a purchasable SKU. |
| `tools/ingest_pi.py` / `tools/refresh_sourced_photos.py` | The photo pipeline. `photo_families.json` matches a real, licensed reference photo (Wikimedia Commons, credited) to a product by category/spec/connector — `sku` allowlist when two products share identical specs but are physically different things (see §5). |

Build: `npm run catalog-site -- data/real/products.csv data/real/images.csv dist`.
Test: `npm test`. Deploy: `npx vercel deploy --prod` (git-push deploys are
blocked by a GitHub identity mismatch — see `docs/OWNER_NOTES.md` §7).

## 1. QUICK START — Use This Skill When

- You're auditing whether a product's page has an honest, accurate visual (not a bare placeholder, not a generic chassis when real connector/port data exists)
- You're adding a new connector family, port-panel type, or topology shape to `connectors.ts` / `diagrams.ts`
- You're deciding whether a product needs a real sourced photo vs. a technical illustration
- You're adding motion to an existing diagram (door opens, ports light up, a signal pulse travels a cable) using the shared scroll engine
- You're widening a solution page's diagram (`Solution.signalChain`) or adding a new solution once real inventory backs every requirement
- You're building a **cinematic hero video** (package → unveiling → macro
  cutaway) for a product category with no real photography — that's the
  `ai-video-prompt-engineering` skill, not this one. Its branch structure
  (cable / HDMI-display / extender-active-device / connector-adapter /
  splitter-hub / PoE) is keyed off the exact same `resolveVisualType()`
  result this skill computes — don't re-derive product category, reuse it.
  Source the physical-detail reference via `open-pinterest` first (CLAUDE.md
  Rule 7), then hand off to that skill for the shot prompts, and scrub the
  finished video to `--p` the same way `rackElevation()`'s door-open motion
  already does (§3).

## 2. THE VISUALIZATION MODEL (real fields, not invented ones)

Every visualization decision is driven by fields that actually exist on `Product`:

```
identity:        sku, slug, categoryId
technicalData:    specs (confirmed only — isConfirmed() filters unverified values),
                  connectors[] (real, per-end tokens: "RJ45", "USB-C", "DC", …),
                  ports[] (PortSpec: id, kind, count, role, label, connectsTo)
presentation:     visualType (explicit override) — falls back to resolveVisualType()'s
                  category-based inference when absent
relationships:    compatibleWith, accessories, commonlyBoughtWith, alternatives,
                  requiredFor — every edge is a real technical dependency, never a guess
research:         third-party standard-level facts (research.families.json), always
                  labelled as research, never mixed unlabelled into confirmed specs
```

**Suitability by shape** (mirrors the real `storyTemplate()` switch):

| Product is a… | Gets |
|---|---|
| Cable / bare connector | `cableStory`: real origin (spool/box), coil, one anatomy scene per **distinct** real connector end (deduped — "HDMI;HDMI" is one drawing, "3.5mm;RCA" is two), construction cross-section if the cable type is known |
| Extender / switch / anything with real `ports` | `deviceStory`: chassis + `devicePanel()` port bank built from the product's own port data, plus a signal-flow list if ports carry a `role` |
| Camera | `cameraStory`: coverage cone from real FOV |
| Rack/cabinet | `rackStory`: `rackElevation()`, a real cabinet body sized from real U-height, door animates open on scroll, filled with the product's real compatible equipment |
| PBX | `pbxStory`: line→PBX→extension topology |
| Anything else | `genericStory`: chassis + confirmed specs, **plus** real connector anatomy scenes if the product has confirmed `connectors` even without a dedicated visualType — this is a real, previously-missed case: 15 real SKUs (USB adapters, DC power adapters, an audio converter) had confirmed connector data and were still rendering a bare chassis until this was wired up |

If a product has none of the above — no real connectors, no real ports, no confirmed specs — it renders nothing rather than a fabricated diagram. That is correct, not a bug to paper over.

## 2.5. MERGED FROM THE "TECHNICAL EXPERIENCE ENGINE" BRIEF

A cinematic teardown brief (packaging → hero → exploded layers → conductor
macro → connector teardown → measurement → spec → application → reassembly,
built on React Three Fiber + GSAP + GLB) periodically resurfaces. That
pipeline is not this project's stack (§0) — don't build it. But three ideas
from it are genuinely useful and are folded in here, translated to real SVG
+ the `--p` engine:

1. **Name the confidence tiers explicitly.** Rule 1 (§5) already forbids
   invented specs; give the levels names when writing new copy or captions:
   `VERIFIED` (from `products.csv`/a real photo), `DEFINITIONAL` (true by
   what the category means — a DC adapter has *some* output connector),
   `RESEARCH` (third-party standard fact, already labelled per §2's
   `research` field), `UNKNOWN` (omit, never guess). A caption or callout
   text should never blur `RESEARCH` into `VERIFIED`.
2. **Numbered progressive layer peel for cable teardown.** `cableStory` →
   `constructionScene` already renders one cross-section with a callout
   list (§2). When a cable's construction data is rich enough (jacket +
   shield + insulation + conductor all present), extend that callout list
   into a numbered sequence (`01 OUTER JACKET`, `02 SHIELD`, …) revealed
   one at a time via staggered `--from`/`--to` windows, same mechanism
   `deviceStory`'s flow list already uses (`product-visuals.ts:520-531`) —
   not a new component, just more callout entries with tighter scroll
   windows. Skip this when construction data is thin (just "PVC jacket, no
   shield") — one callout is more honest than four padded ones.
3. **Depth scales with real data, not a fixed scene count.** A product
   with a spool origin + 2 connector ends + known construction earns the
   full `cableStory` chain; a product with just confirmed specs gets
   `genericStory`'s spec table. This is already how `storyTemplate()`
   routes (§2) — the brief's "technical depth score" is just naming what
   the switch already does. Don't add a literal 0–100 score field; the
   routing decision is the score.

Explicitly **not** adopted: GLB/WebGL exploded 3D, screen-space
label-anchoring math (SVG coordinates already are the anchor — no
projection step needed), physical-material PBR shading, a packaging
unboxing render (that's `ai-video-prompt-engineering`'s rare, explicitly-
approved hero-video case per §1, not a per-product default), and a
separate 3D connector-teardown scene (macro SVG anatomy in `connectors.ts`
already covers this at the fidelity real data supports).

## 3. THE REAL MOTION ENGINE

One shared driver (`src/site/motion.ts`), not GSAP. A `<section data-scene>`
gets a `--p` custom property (0→1) as its scroll track passes the viewport.
Any element inside declares the slice of that scroll it owns:

```html
<g class="stage-item" style="--from:0.2;--to:0.4">…</g>
```

```css
.stage-item {
  --local: clamp(0, calc((var(--p) - var(--from)) / (var(--to) - var(--from))), 1);
  opacity: var(--local);
}
```

`--local` is a free-standing 0→1 progress value — consume it for **any**
transform, not just opacity. Two real, shipped examples:

- **Edges draw themselves in**: `.dg-edge { stroke-dasharray: 1; stroke-dashoffset: calc(1 - var(--local, 1)); }`
- **A cabinet door swings open on its hinge**: a 2D `scaleX` trick anchored at `transform-origin: left` (the same illusion a page-turn uses), timed to finish *before* the real equipment inside starts revealing — `.dg-door.stage-item { transform-origin: left center; transform: scaleX(calc(1 - var(--local) * .94)); }`. The base `.stage-item` opacity rule is overridden to a fixed value first, since a door's "closed" state must start *visible*, not faded in from nothing the way a generic reveal does.

**Never skip the reduced-motion/small-screen fallback.** `motion.ts` pins
every `.stage-item` to `opacity:1; transform:none` under
`prefers-reduced-motion` and on screens ≤860px — the scene's *resolved end
state*. For a fade-in element that's correct. For anything whose resolved
end state is NOT "transform: none" (a door that should end up *open*, not
literally untransformed/closed), you must add your own higher-specificity
override in the same two media queries, or reduced-motion users see a
broken freeze-frame instead of the finished composition. This is the
single most common way a new animation looks fine on desktop and broken
for a third of real visitors.

## 4. WIRING IN REAL-WORLD VISUAL REFERENCES

Per the standing frontend routing rule: any new diagram/motion **look** —
not the underlying technical accuracy, the *style* (composition, color
weight, how a reveal reads) — routes through the `open-pinterest` skill
first, the same way the homepage hero's node-graph styling and the
keystone-jack photo were sourced this session.

The pattern, already established in `design-refs/pinterest/<topic>/README.md`:

1. Search real references for the *technique*, not the product (e.g. "IDC
   punch-down termination macro photography" for a keystone animation, not
   "keystone jack" — you already have the real jack's shape from
   `connectors.ts`/a sourced photo; what you're borrowing is *how the
   motion reads*).
2. Never ship the reference image or video as-is — `design-refs/pinterest/`
   is `.gitignore`d for exactly this reason. Re-implement the *technique*
   natively as inline SVG/CSS using the real motion engine in §3.
3. Write down what was actually applied (one line: the technique + which
   function implements it) in the topic's README, so the next session
   doesn't re-spend a Pinterest round-trip on a look already solved —
   see the existing `network-diagram/README.md` for the format.

For product **photography** specifically (not motion/style references),
Pinterest is the wrong source — see §5. Every real sourced photo in this
catalog came from Wikimedia Commons under a checkable CC license, credited
in `photo_families.json`. Pinterest re-pins aren't licensed for reuse in a
commercial catalog; that's a legal distinction, not a style preference.

If a licensed candidate photo is blurry, low-res, screenshotted, or
otherwise too degraded to confirm connector type/count or read the label,
run the `image-restoration-accuracy` skill on it **before** deciding it
qualifies for `photo_families.json` — only a CONFIRMED identity result
clears it; PROBABLE/UNKNOWN means keep looking for a better source rather
than ingesting a guess.

## 5. RULES & CONSTRAINTS (the ones that have actually caught real bugs)

### A real photo is never replaced by a diagram, illustration, or 3D scene

**This is a hard rule, not a style preference — a real sourced photo (Wikimedia
Commons or an actual invoice/product photo, per §5.5 step 4) and a diagram/
illustration/3D scene are never the same slot.** The photo answers "what does
this look like"; a diagram/scene answers "how is it built" — they are additive,
never substitutes for each other. Concretely, on any product page:

- `pv-hero-media` (the real photo, `<img class="pv-hero-img">`) is never
  removed, hidden, or overwritten by a diagram, illustration, or the R3F/GSAP
  scene from §2.5 — regardless of how good the diagram is.
- A diagram/scene goes only in its own scroll-story section
  (`anatomyScenes()`'s `pv-conn-art`, `constructionScene()`'s `pv-xsec-art`,
  or an equivalent new slot) — never stacked over, before, or in place of the
  hero photo.
- If a product has no real photo yet, the honest state per §5.5 step 5 is a
  diagram/illustration filling the *diagram's own slot*, or nothing — never a
  diagram standing in for where the photo belongs. Don't blur the two roles
  to paper over a missing photo.

This already caused one real mistake this session (an early R3F prototype was
mounted directly above the hero photo instead of inside the connector-anatomy
scene) — fixed, but flagging it here so no session repeats it, including any
concurrent session working on diagrams, photos, or the §2.5 3D pipeline.

### Never invent — and watch for the specific way this project's data breaks

**Rule 1:** No specification, connector, dimension, or relationship ships
unless it traces to `products.csv`, a real invoice photo, or a definitional
fact about what the product physically is (a DC-rated power adapter has
some output connector; that is not a guess, it's what "power adapter"
means — but *which shape* still needs a real photo check, not assumption).

**Rule 2 — the recurring real failure mode is two products sharing
identical recorded specs while being physically different things.**
Every one of these actually happened this session:

- A keystone jack and a box of loose RJ45 plugs both carried
  `deviceType=keystone;connectors=RJ45` — the photo matcher couldn't tell
  them apart until an explicit `sku` allowlist was added to
  `photo_families.json`.
- A male and a female SMA connector share identical
  category/spec/connector data with no gender field — a first attempt at
  adding the male's photo silently overwrote the female's real existing
  photo. Caught before committing, fixed with the same `sku` allowlist
  mechanism.
- A mono and a stereo 6.35mm plug both matched the single `"6.35mm"`
  connector token — the shared macro was hardcoded to always draw the
  stereo (TRS, two-band) shape. Fixed by giving the mono SKU a distinct
  token (`"6.35mm-mono"`) checked *before* the general case.
- A cabinet PDU and a cable-management bar, filed under the `cabinets`
  category (correctly — they're cabinet accessories), inherited that
  category's `heightU`/`mounting`/`glassDoor` attribute schema by
  copy-paste, so a power strip's spec table showed "Glass door: No" — not
  a real fact about a power strip, a category-schema mismatch.

**The fix is always the same shape**: before trusting a match, ask "is
there a second real product this exact rule would also match, and is it
actually the same thing?" — grep for siblings sharing the same
category+spec+connector combination before shipping a new `photo_families`
entry or connector-token mapping.

**Rule 4 — a replacement photo must match the REAL product's actual look
(color, material, connector finish, construction), not just be a nicer or
cleaner photo of the same category.** This is a hard rule, added after a
real mistake in the 2026-08-23 HDMI-family photo fix: the fiber-optic HDMI
family's real supplier PO reference (an embedded image in the invoice
xlsx, extracted via `openpyxl`/zipfile — see §5.6) showed a specific real
cable, and the owner had already seen its cream/off-white color in the
live (buggy) catalog page. A first attempt swapped in a striking dark-grey
"premium AOC" cable found via generic Pinterest search — visually
higher-production-value, and still genuinely a fiber-HDMI-shaped cable,
but the **wrong real color/finish**, caught immediately by the owner
("this is not similar to the cable in the plastic bag"). Concretely:

- When a real reference photo exists (a supplier PO's embedded image, an
  existing "bad but real" catalog photo, a photo the owner points at),
  that reference is the ground truth for color/material/connector-finish
  — not just for "is this the right connector family." A cream cable
  cannot be swapped for a premium-looking grey one because grey photographs
  better; that is presentation bias overriding the real fact.
- Before finalizing a replacement photo, explicitly compare it against
  the real reference on: overall cable color, connector shell color/
  finish (gold vs silver vs colored plastic), and any visible real
  construction detail (braided vs smooth jacket, molded vs metal shell) —
  not just "is this generically the right kind of cable."
- If the *only* available real reference is low-quality (blurry, tiny,
  screenshot, barcode-obscured), that still fixes the color/material
  ground truth even when it doesn't fix the composition/resolution — use
  `image-restoration-accuracy` skill's inspect step to confirm what's
  actually confirmable (CONFIRMED vs PROBABLE vs UNKNOWN) before treating
  any attribute as free to change.
- This applies to every future photo replacement in this catalog, not
  just HDMI cables — any session (this one or a different account/AI)
  fixing a duplicate-photo or wrong-photo bug must check the real
  reference's color/material first, and only then look for a
  cleaner-quality Pinterest photo *of that same real appearance*.

**Rule 3:** A regex used to compute a relationship (e.g.
`add_relationships()`'s SKU-family grouping in `tools/ingest_pi.py`) must
be the *same* regex everywhere it's used. This project shipped with two
subtly different versions — one handled decimal lengths (`[\d.]+`), the
other didn't (`\d+`) — so `VGA-1.5M` built its family correctly but could
never look itself back up, silently shipping an empty `alternatives` field
on 11 real SKUs. One shared `family_key()` function closed it. If you ever
see the same pattern expressed twice nearby, that's the bug before it's
found, not a style nit.

### Visualization suitability

Not every product needs a diagram. A cable ties, a rack cage-nut bag, a
duct rodder — these have no real connector/port/construction data to draw
from, and a bare spec table (or nothing, if specs are also empty) is the
honest state. Do not build a generic decorative illustration to fill the
space; that is exactly the "decorate, don't explain" failure this skill
exists to prevent.

### Performance & accessibility

- Every diagram is inline SVG — no requests, no external assets.
- Photos are downscaled to 900px progressive JPEG at ingest (throttled 3G
  is the real target audience, not a hypothetical).
- `prefers-reduced-motion` and ≤860px both collapse every scene to its
  finished composition — see §3 for the one non-obvious failure mode.
- Hotspots (`data-hotspot`) are real focusable elements, not just
  hover-only — keyboard users get the same callout detail.

## 5.5. NEW-PRODUCT ONBOARDING CHECKLIST

Run this, in order, every time a new product enters the catalog. It's the
research discipline the whole honesty architecture depends on — most of it
is already how this skill and `ai-video-prompt-engineering`'s "per-product
workflow" operate, formalized here as one checklist instead of scattered
across two files.

**No AI video/image generation in this checklist — that's a separate,
rare, explicitly-approved case (the one shared cable-coil hero asset), not
a per-product step.** Every new product's visual comes from the existing
hand-rolled SVG/scroll template system (§2-3), selected automatically by
`resolveVisualType()`. The work here is verifying real data and, only when
a genuinely new *shape* of component shows up (a connector family or port
type `connectors.ts`/`diagrams.ts` can't already draw), building one more
hand-authored SVG template in that same system — not reaching for a video
generator.

1. **Identity** — real SKU, model, manufacturer, category from
   `products.csv`. Don't confuse a family name with an exact model, or a
   reseller SKU with a manufacturer part number.
2. **Real data first** — pull `technicalData.specs` (confirmed only),
   `connectors[]`, `ports[]`. Anything not in the record and not a public
   standard (an HDMI pinout, T568B, etc.) gets left out, never inferred
   "because that's typical for this category" (Rule 1, §5).
3. **Sibling check** — before trusting any new `photo_families.json`
   match or connector-token mapping, grep for a second real product
   sharing the same category+spec+connector combination that is
   *physically different* (Rule 2, §5 — this has caught 4 real bugs
   already: keystone-vs-loose-plugs, male-vs-female SMA, mono-vs-stereo
   6.35mm, PDU-vs-cable-bar).
4. **Real photo, sourced correctly** — Wikimedia Commons only, CC-licensed,
   credited. Open the actual file page, confirm it depicts *this exact
   component* (not a lookalike, not the socket when the product is the
   plug, not a bundled unrelated item in frame) before downloading. Never
   trust a prior session's "already has a usable crop" note without
   re-opening the actual image — that claim has been wrong before (an
   invoice-row crop turned out to be a completely different product).
   Optimise to the catalog's real convention: `MAX_EDGE=900`,
   `MIN_EDGE=400` upsampled, JPEG quality 78 progressive (`tools/
   ingest_pi.py`'s `optimise()` — replicate exactly, don't reinvent).
5. **No real photo found** — the existing SVG/scroll template for that
   `resolveVisualType()` is the correct, honest end state. Do not build a
   one-off decorative illustration or reach for AI generation to fill the
   gap — a structured placeholder is more honest than an invented visual.
6. **Wire it, rebuild, verify visually** — add the row to `images.csv`
   (or `photo_families.json` + `sourced_photos/` only for a genuine
   shared-family case, with a `sku` allowlist if any sibling risk exists),
   rebuild, screenshot the actual page (Playwright, headless — see
   `reference_local_playwright_screenshots` memory), confirm it's really
   the right component before calling it done.
7. **Frontend bar, if a new template is genuinely needed** — a new
   connector/topology shape gets the same anti-slop bar as any frontend
   work: `open-pinterest` for the *motion/composition technique* only
   (§4), never product photography from there, then implement natively in
   this project's own SVG/CSS/`--p` scroll engine (§2-3) — no new
   dependency, no generic templated look.

## 6.5. TECHNICAL REFERENCE LIBRARY (real, public standards — DEFINITIONAL tier)

Verified from real standards documentation, not per-product guesses (§2.5 tier
`DEFINITIONAL` — a public standard's pin functions are a fact about the connector
family, true for every real product using it, distinct from an unverified per-SKU
claim). Use these to add genuinely accurate pinout/wiring annotations to a connector
scene or macro — a real "what does pin 2 do" beats a bare shape drawing every time,
and this catalog carries all of these connector families.

- **RJ45 / T568A vs T568B (ANSI/TIA-568)**: two real wiring standards, not one —
  T568A puts the green pair on pins 1-2, orange on 3-6; T568B swaps them, orange on
  1-2, green on 3-6. Both perform identically as long as **both ends of one cable use
  the same standard** — never present one as "more correct," they're equivalent, only
  consistency matters. A real Cat5e/6 cable carries 4 twisted pairs: blue, orange,
  green, brown.
- **HDMI Type-A (19-pin)**: real named pin functions worth surfacing beyond "19 gold
  contacts" — TMDS data/clock pairs (the actual video signal), **CEC** (single-wire
  device control, e.g. one remote controlling a TV+receiver), **DDC/+5V** (EDID
  handshake — how the source learns the display's supported resolutions), **HPD**
  (Hot Plug Detect — how the source knows a display is connected at all), and
  **ARC/eARC** on the newer standard (audio return over the same cable). Mini/Micro
  HDMI carry the same 19 signals in a smaller shell — same wiring facts apply.
- **DB9 / RS-232 serial**: only 3 pins carry a basic connection — **pin 2 = RXD**
  (receive), **pin 3 = TXD** (transmit), **pin 5 = GND**. Pin 1 is DCD (Data Carrier
  Detect), part of full modem-control signaling most simple serial links don't use.
  Worth noting on any DB9/RS-232 product page since "why does a 9-pin connector only
  need 3 wires for most uses" is a real, useful thing to explain.
- **XLR (3-pin, AES14-1992 / IEC 60268-12)**: **pin 1 = ground/shield, pin 2 = hot
  (+), pin 3 = cold (−)** — universal across professional audio, this is what
  "balanced audio" physically is: pin 3 carries an inverted copy of the signal, so
  noise picked up equally by both conductors cancels at the receiving end. This is a
  genuinely satisfying "how it works" fact for an XLR product's construction scene.

- **VGA (DE-15, analog RGB)**: 3 analog color signals (R/G/B, 0.7V peak-to-peak into
  75Ω), separate HSync/VSync timing lines, and a real DDC (I²C) channel on pins 12/15
  — the same "source reads the display's real capabilities" concept as HDMI's DDC,
  just older. Worth noting on VGA cable/adapter pages as "why does this thin cable
  need 15 pins" — most are colour+sync, only 2 carry the actual capability handshake.
- **USB-A (4-pin)**: VBUS (+5V), D+/D− (data pair), GND — the simple case.
- **USB-C (24-pin)**: real distinguishing feature is symmetry — 4 VBUS + 4 GND pins
  (for reversibility and higher current), 2 **CC pins** (only one active at a time —
  this is the actual mechanism behind "plug it in either way, it just works," and how
  USB Power Delivery negotiation happens), plus SuperSpeed TX/RX differential pairs
  that can carry USB 3.x data or, in Alt Mode, DisplayPort/Thunderbolt video instead of
  USB data on the same physical pins. A USB-C cable's real capability (charging-only vs
  data vs video-alt-mode) depends on which of these pins the cable actually wires
  through — a real, useful, verifiable fact when the catalog's own spec data says which.
- **BNC / coaxial, 50Ω vs 75Ω — a real compatibility hazard, not just two flavors**:
  50Ω is the RF/data standard, 75Ω is the video/broadcast standard, and mixing them
  causes real signal loss (~5% per mismatch point) from impedance-mismatch reflection
  — worth flagging explicitly on any BNC surveillance/video product, since a real
  customer mistake (grabbing a 50Ω BNC cable for a 75Ω CCTV run) is a genuine, common
  failure mode this catalog's own construction scene could pre-empt.
- **RCA / composite & component video color coding**: composite = yellow (video) +
  white/red (stereo audio); component = green (Y/luminance) + blue (Pb) + red (Pr),
  **and when paired with white/red stereo audio there are deliberately two red plugs**
  (Pr video + right-channel audio) — a real, non-obvious point worth a callout since
  it looks like a wiring mistake to an unfamiliar customer but is the correct standard.
- **IEC 60320 power connectors (C13/C14, C19/C20)** — real current ratings, not just
  "bigger plug": **C13/C14 rated 10A/250V (2500W)**; **C19/C20 rated 16A/250V (up to
  4000W)** — the physically larger C19/C20 shape exists specifically so a
  higher-current device can't accidentally be plugged into a C13/C14-rated circuit.
  Directly relevant to this catalog's PDU/cabinet-accessory products (§5's PDU/
  cable-bar schema-mismatch bug already lives in this exact category).
- **3.5mm/6.35mm audio jacks — TS vs TRS vs TRRS is a real, verifiable difference,
  not just "headphone jack"**: TS (mono, tip=signal/sleeve=ground, one insulating
  band) vs TRS (tip=left/ring=right/sleeve=ground for unbalanced stereo, OR
  tip=hot/ring=cold/sleeve=ground for balanced mono line-level — same physical
  wiring, different real meaning depending on application) vs TRRS (adds a mic
  channel). This directly extends the skill's own already-documented Rule 2 bug (a
  mono 6.35mm SKU getting the stereo/TRS shape by mistake) — the physical band-count
  on the plug is the real, checkable tell.
- **DisplayPort**: real distinguishing facts vs. HDMI worth surfacing — a **Main Link**
  of up to 4 lanes carrying the actual video/audio data (DP 2.0 pushes up to 20Gbps
  per lane), a separate bidirectional **AUX channel** for link training/EDID/device
  control (DisplayPort's equivalent of HDMI's DDC), and its own **HPD** (Hot Plug
  Detect, 3.3V signal). The one real, useful differentiator from HDMI: DisplayPort
  supports **MST (Multi-Stream Transport)** — daisy-chaining multiple monitors off one
  port — which HDMI does not do natively. Worth a callout on any DisplayPort/HDMI
  converter product specifically because it explains a real capability gap, not just
  "these are both video cables."
- **DVI-D vs DVI-I, single-link vs dual-link**: DVI-D is digital-only; DVI-I adds 5
  analog pins for VGA-signal compatibility via a passive adapter. Single-link (19/25
  pins for D/I) tops out at 1920×1200@60Hz; dual-link doubles bandwidth for up to
  2560×1600@60Hz — a real, checkable spec difference worth surfacing on any DVI
  product/adapter page rather than treating all DVI cables as interchangeable.
- **SMA / N-type RF connectors**: both real 50Ω RF connector families (SMA
  subminiature screw-coupling, rated to 18GHz+; N-type is the larger, more rugged
  weatherproof-capable version of the same 50Ω RF concept) — same impedance-matching
  logic as the BNC 50Ω/75Ω note above applies here too.
- **RJ11 (6P4C, telephone)**: only the center 2 of its 6 positions (positions 3-4)
  actually carry a single phone line in the common case — real, useful "why does a
  6-slot connector only need 2 wires for one line" fact, same shape as the DB9/RS-232
  note above.
- **DB25 (parallel port)**: 8 data pins + 4 output-control + 5 input-control + 8
  ground — relevant to this catalog's DB25/serial-adapter SKUs as real "why so many
  pins for what feels like a simple cable" context.
- **DC barrel power connectors**: two real, independent variables, and this is a
  genuine "don't invent" case, not just trivia — **size** (5.5mm OD / 2.1mm ID is the
  common 12-24V case, but 2.5mm ID and other combinations exist and are NOT
  interchangeable) and **polarity** (center-positive is the dominant convention, but
  center-negative genuinely exists in real products — never state a specific SKU's
  polarity unless the catalog's own spec data or a real datasheet confirms it; this is
  exactly the kind of fact Rule 1 (§5) says must trace to real data, not "most DC
  barrels are like this so this one probably is too").
- **RJ45 shell wired for RS-485 (not standard Ethernet)** — the differential-signaling
  *concept* is real and DEFINITIONAL (two wires carrying opposite-polarity copies of
  the same signal so induced noise cancels at the receiver, the same principle as
  twisted-pair Ethernet and balanced XLR audio above), but **the actual pin assignment
  is explicitly NOT standardized across manufacturers** — real sources confirm this
  varies device-to-device even though it looks like a normal RJ45 jack. Never present
  a specific pin mapping for this catalog's `RJ45 (RS485)` SKU as fact without a real
  manufacturer datasheet behind it; the honest technical note is "this connector
  carries RS-485 differential signaling, not Ethernet — pin mapping is
  device-specific, consult the connected equipment's documentation," not a guessed
  pinout diagram.

**Boundary — don't overreach past what's actually public and stable:** these are
connector-family facts (true for any real product using that connector), not
manufacturer-specific pinouts for a proprietary port. Don't extend this pattern to
guess a specific product's internal wiring without a real datasheet behind it — same
Rule 1 (§5) boundary as everything else in this skill.

**Where this data actually goes**: not just this reference doc — a connector-family
fact that applies to a real SKU (e.g. every RJ45 product gets the T568A/B note, every
IEC C13/C14 accessory gets the 10A/250V rating) is DEFINITIONAL-tier and belongs in
that SKU's own `technical_notes_ar`/`technical_notes_en` fields in `products.csv`
alongside its scene/diagram callouts — the catalog's real technical-depth upgrade
(tracked in the Handoff Log's "202-SKU upgrade pass") means actually writing these
facts into the real product data, not leaving them stranded in this skill file.

**How it surfaces on the page — an expandable "In-depth details" disclosure, not a
wall of text on every card.** Zoher's explicit ask: customers who want the full
pinout/wiring depth should be able to get it, but it shouldn't clutter the default
product view for someone who just wants to know if the cable is the right length.
The zero-dependency answer already matches this site's own stack (§0) — a native
`<details>`/`<summary>` element:

```html
<details class="pv-depth">
  <summary>In-depth technical details</summary>
  <!-- §6.5 facts for this SKU's real connector(s), plus any construction-scene
       content that's too long for the always-visible callout list -->
</details>
```

Real reasons this beats a JS-driven modal/accordion for this specific site: works
with zero JavaScript (survives a slow/failed script load on 3G), is natively
keyboard-and-screen-reader accessible (no ARIA reimplementation needed —
`<details>`/`<summary>` already has correct semantics built in), and needs no new
dependency or motion-engine wiring. Style the `<summary>` marker and open/close
transition with plain CSS (`::marker`, `[open]` selector) — no JS required even for
the visual polish. This becomes the real home for §6.5's facts on every product page,
not a replacement for the existing always-visible spec table/callouts, an addition
for the reader who wants more.

## 6.6. CONFIRMED REAL GAP — every diagram is missing accessible text

Checked directly against the real code (`diagrams.ts`, `connectors.ts`): **all 7 SVG
diagram functions set `role="img"` but none include a `<title>` element.** Per
WCAG/ARIA SVG accessibility guidance, `role="img"` with no accessible name (`<title>`
as the SVG's first child, or `aria-label`) announces to a screen reader as an
unlabeled, empty graphic — every technical diagram on the site is currently invisible
to a screen reader user, not just "less detailed." A `<title>` short name (e.g. "RJ45
connector anatomy diagram") plus, where useful, a `<desc>` immediately after it for a
longer real description, are cheap, drawing-preserving fixes — never invented as
filler text, the title/desc should say what the diagram actually shows, matching the
same honesty bar as everything else here. This is a real, confirmed, sitewide gap to
close, not a hypothetical audit finding.

## 6.7. IMAGE FORMAT — a real, unshipped 3G-target win

The photo pipeline (`tools/ingest_pi.py`) currently ships plain progressive JPEG at
900px/quality 78. Verified 2026 data: AVIF produces 20-30% smaller files than
JPEG/WebP at equivalent visual quality for photographic content specifically (product
photos are exactly this case — AV1's block-partitioning holds detail better than
JPEG/WebP at a tight bitrate), and AVIF now has ~94% global browser support. The one
real gap: **older pre-2021 Android devices — exactly this site's stated target
audience — are the actual AVIF holdout**, so AVIF must ship with a WebP (not JPEG)
fallback via `<picture>`, never AVIF-only. This is a concrete, still-unshipped
optimization directly aligned with §0's stated performance priority — worth
implementing in `ingest_pi.py`'s `optimise()` once picked up, not just a filed idea.

## 6.8. WHY THE CUSTOM MOTION ENGINE STAYS, RECONFIRMED WITH REAL 2026 DATA

`motion.ts`'s own comment (§0/§3) rejected native CSS `animation-timeline: view()` for
"uneven support" — re-checked in 2026: desktop browser support is now genuinely high
(~84%+, all major engines), so the original reasoning as stated is partly stale. It
stays the right call anyway, for two reasons that hold regardless of desktop support
numbers: (1) this site's real audience is **older Android devices** specifically,
where OS/WebView age lags desktop browser stats significantly — the relevant number
isn't "global desktop support," it's "how old is a typical low-end Android WebView in
Syria," which stays a real risk; (2) a pure-CSS timeline has no JS-readable value to
hand to a **non-CSS consumer** — the §2.5 R3F/WebGL scene needs a per-frame numeric
scroll-progress value to drive a `camera.position`, and CSS custom properties aren't
directly queryable by JS without the same `getComputedStyle` poll `Scene.tsx` already
does (which works identically whether `--p` is set by JS or by a native CSS timeline).
Net: keep `motion.ts` as the one shared source of `--p` — this is a confirmed,
evidence-based decision now, not an unchecked inherited assumption.
